# 1. What Is Deployment?

During development, you might run an app on your computer:

```bash
uvicorn main:app --reload
```

To make it available to other people over the internet, you deploy it to a server and configure networking, a process manager or application server, a domain, HTTPS, and monitoring.

A common architecture is:

```text
Browser
   |
   v
Domain / DNS
   |
   v
Nginx (web server / reverse proxy)
   |
   v
Gunicorn or Uvicorn
   |
   v
Python Application
   |
   v
Database / External Services
```

This is a common pattern, not a requirement for every hosting environment. Some cloud platforms manage several of these components for you.

---

# 2. WSGI vs ASGI

Python web applications need a standard interface to communicate with application servers.

## 2.1 WSGI

**WSGI** means **Web Server Gateway Interface**. It is commonly used by traditional synchronous Python web applications, including many Flask and Django deployments.

Typical architecture:

```text
Browser -> Nginx -> Gunicorn (WSGI worker) -> Flask/Django
```

## 2.2 ASGI

**ASGI** means **Asynchronous Server Gateway Interface**. It supports asynchronous applications and long-lived connections such as WebSockets. It can also serve ordinary HTTP requests.

Typical architecture:

```text
Browser -> Nginx -> Uvicorn (ASGI server) -> FastAPI
```

## 2.3 Comparison

| Feature | WSGI | ASGI |
|---|---|---|
| Full name | Web Server Gateway Interface | Asynchronous Server Gateway Interface |
| Typical use | Traditional synchronous apps | Synchronous and asynchronous apps |
| WebSockets | Not supported by WSGI itself | Supported |
| Common frameworks | Flask, Django in WSGI mode | FastAPI, Starlette, Django in ASGI mode |
| Example server | Gunicorn with WSGI worker | Uvicorn; compatible ASGI worker setups |

ASGI does not automatically make every application faster. Blocking code, slow database queries, and inefficient algorithms can still cause performance problems.

## 2.4 Synchronous and asynchronous code

Synchronous example:

```python
import time

def get_message():
    time.sleep(2)
    return "Hello"
```

Asynchronous example:

```python
import asyncio

async def get_message():
    await asyncio.sleep(2)
    return "Hello"
```

`await` allows an event loop to run other eligible tasks while an asynchronous operation is waiting. Calling blocking functions inside an async route can still block the event loop.

# 3. What Is an Application Server?

An application server runs your Python application and handles requests using the appropriate interface.

Examples include:
- Gunicorn
- Uvicorn
- Waitress
- Daphne

Remember the distinction:

- **Application:** Your Python routes and business logic.
- **Application server:** Runs the application and handles requests.
- **Nginx:** Often receives public traffic and forwards it to the application server.

---

# 4. Gunicorn

**Gunicorn** is commonly used to serve WSGI applications such as Flask and WSGI-mode Django applications on Linux servers.

Example `app.py`:

```python
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello from Flask!"
```

Install:

```bash
pip install gunicorn
```

Run:

```bash
gunicorn app:app
```

`app:app` means:
- First `app`: the Python module (`app.py`).
- Second `app`: the application object inside that module.

Bind to a local address and port:

```bash
gunicorn --bind 127.0.0.1:8000 app:app
```

Nginx can forward requests to this local address. The example assumes a Linux/macOS-like environment; Windows production deployment commonly uses a different approach.

> Gunicorn is traditionally associated with WSGI. It can also manage ASGI applications when configured with a compatible ASGI worker. The worker type and package must match your setup.

---

# 5. Workers

A **worker** is a process or worker instance that handles application work.

```text
Gunicorn Master Process
       |
       +---- Worker 1
       +---- Worker 2
       +---- Worker 3
```

Multiple workers can handle requests concurrently and use more than one CPU core. Each worker also consumes memory, so more workers are not always better.

Example:

```bash
gunicorn --workers 3 --bind 127.0.0.1:8000 app:app
```

This requests three workers. Choose a suitable count based on memory, CPU, request patterns, and load testing rather than copying a number blindly.

---

# 6. Uvicorn

**Uvicorn** is an ASGI server commonly used with FastAPI and Starlette.

Example `main.py`:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
async def home():
    return {"message": "Hello from FastAPI!"}
```

Install:

```bash
pip install "uvicorn[standard]"
```

Development command:

```bash
uvicorn main:app --reload
```

Here:
- `main` is the module (`main.py`).
- `app` is the FastAPI object in that module.
- `--reload` restarts the development server when code changes.

Do not normally use `--reload` in production.

A simple server command:

```bash
uvicorn main:app --host 127.0.0.1 --port 8000
```

## 6.1 Uvicorn workers

Uvicorn can run multiple worker processes:

```bash
uvicorn main:app --host 127.0.0.1 --port 8000 --workers 4
```

This requests four workers. Process management options can vary by platform and deployment approach.

Another option is to use Gunicorn with a compatible ASGI worker. For installations using the `uvicorn-worker` package:

```bash
pip install gunicorn uvicorn-worker
```

```bash
gunicorn main:app \
    --workers 4 \
    --worker-class uvicorn_worker.UvicornWorker \
    --bind 127.0.0.1:8000
```

Check the current documentation for the worker package and class supported by your installed versions.

## 6.2 Gunicorn vs Uvicorn

| Gunicorn | Uvicorn |
|---|---|
| Commonly serves WSGI applications | Serves ASGI applications |
| Often used with Flask/Django WSGI apps | Often used with FastAPI/Starlette |
| Supports different worker types | Provides ASGI request handling |
| Can manage compatible ASGI workers | Can run directly or under a process manager |

Beginner rule of thumb:
- Flask: Gunicorn with a WSGI worker on a suitable server.
- FastAPI: Uvicorn.
- Larger deployments: choose process management based on application needs and hosting platform.

# 7. Development vs Production

Development:

```bash
uvicorn main:app --reload
```

A production deployment usually needs:
- Development reload disabled.
- A suitable application server and process manager.
- Correct environment variables and protected secrets.
- A reverse proxy or hosting platform configuration.
- HTTPS.
- Logs, monitoring, and restart handling.
- Security updates and backups.

Deployment is more than just running one command.

# 8. Nginx Basics

**Nginx** is web server software often used as a reverse proxy. It can:
- Accept public HTTP and HTTPS traffic.
- Forward requests to application servers.
- Serve static files.
- Handle TLS/HTTPS.
- Route requests by domain or path.
- Apply request limits and timeouts.
- Write access and error logs.

Common arrangement:

```text
Internet
   |
   v
Nginx :80 / :443
   |
   v
127.0.0.1:8000
   |
   v
Python Application
```

Port `80` is commonly used for HTTP and `443` for HTTPS.

## 8.1 Basic reverse proxy configuration

For a FastAPI application running at `127.0.0.1:8000`:

```nginx
server {
    listen 80;
    server_name example.com www.example.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

This tells Nginx to forward requests for the specified domain to the local application server.

`X-Forwarded-*` headers pass information about the original request. Configure the application to trust proxy headers only from known, trusted proxies; otherwise clients may spoof them.

On many Ubuntu/Debian systems, site configurations are commonly stored in `/etc/nginx/sites-available/` and enabled through `/etc/nginx/sites-enabled/`. Locations vary by distribution.

Test configuration before reloading:

```bash
sudo nginx -t
```

If valid, reload Nginx on a systemd-based Linux server:

```bash
sudo systemctl reload nginx
```

# 9. What Is a Reverse Proxy?

A **reverse proxy** accepts requests from clients and forwards them to backend servers.

Without a reverse proxy, someone might access an app directly using an address and port:

```text
http://203.0.113.10:8000
```

With a reverse proxy, the user visits:

```text
https://example.com
```

Nginx receives the request and forwards it internally to the application server.

Benefits include:
- One public entry point.
- Central place to configure HTTPS.
- Routing for multiple applications or domains.
- Efficient static file delivery.
- Internal application ports can remain private.
- Access and error logs.

A reverse proxy does not automatically make an application secure. Firewall rules, application security, updates, and correct configuration remain important.

# 10. Domain Configuration and DNS

A **domain name** is a readable name used to access a service, for example:

```text
example.com
api.example.com
```

DNS maps domain names to records that help browsers find the correct destination.

## 10.1 Common DNS record types

| Record | Purpose |
|---|---|
| `A` | Maps a name to an IPv4 address |
| `AAAA` | Maps a name to an IPv6 address |
| `CNAME` | Makes one name an alias of another name |
| `MX` | Specifies mail servers |
| `TXT` | Stores text used for verification and other purposes |

Example:

```text
example.com  A  203.0.113.10
```

`203.0.113.10` is a documentation example address, not a real server address to use.

## 10.2 Typical domain setup

1. Obtain a domain name.
2. Configure DNS with the domain's DNS provider.
3. Point the domain to the server IP or hosting provider's specified target.
4. Configure Nginx or the hosting platform for the domain.
5. Configure HTTPS.
6. Test the website.

DNS changes may take time to appear everywhere because of caching and TTL settings.

# 11. HTTP, HTTPS, SSL, and TLS

## 11.1 HTTP

HTTP is a protocol used for communication between clients and web servers.

```text
http://example.com
```

Ordinary HTTP does not provide transport encryption by itself.

## 11.2 HTTPS

HTTPS is HTTP carried over TLS encryption.

```text
https://example.com
```

HTTPS helps protect data in transit against eavesdropping and tampering. A certificate also helps the browser verify the server's identity.

## 11.3 SSL vs TLS

SSL is the older predecessor to TLS. SSL is obsolete and should not be enabled. Modern secure HTTPS uses TLS.

The phrase **SSL certificate** is still widely used informally for a certificate used with HTTPS.

## 11.4 Why HTTPS matters

HTTPS is important when users send:
- Login credentials.
- Personal information.
- API requests.
- Session cookies.
- Payment-related information.

HTTPS protects data in transit, but it does not automatically fix insecure application code or protect a compromised server.

## 11.5 How HTTPS fits into deployment

```text
Browser
   |
   | HTTPS / TLS
   v
Nginx :443
   |
   | Local/private connection
   v
Gunicorn / Uvicorn
   |
   v
Python Application
```

Nginx often handles the public TLS connection and forwards requests to the application server over a local interface or socket. A cloud load balancer or hosting platform may handle HTTPS instead.

## 11.6 Certificates

Let's Encrypt is a certificate authority that provides domain-validated TLS certificates. Certbot can help obtain and renew certificates on supported systems.

General process:
1. Point the domain to the server.
2. Allow the required inbound web traffic.
3. Configure the web server for the domain.
4. Install a supported ACME client.
5. Obtain and install the certificate.
6. Test HTTPS.
7. Confirm renewal is configured.

Check the current official instructions for your operating system and Nginx setup rather than copying commands intended for a different environment.

# 12. Logging

**Logging** means recording useful events while an application runs.

Logs help answer:
- Did the application start?
- Did a request fail?
- Did a database connection fail?
- What error occurred?
- When did it happen?

Python includes a `logging` module.

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s"
)

logging.info("Application started")
logging.warning("A sample warning")
logging.error("A sample error")
```

Possible output:

```text
2026-10-09 10:00:00 INFO Application started
2026-10-09 10:00:01 WARNING A sample warning
2026-10-09 10:00:02 ERROR A sample error
```

The timestamp and exact output depend on the environment.

## 12.1 Common log levels

| Level | Purpose |
|---|---|
| `DEBUG` | Detailed diagnostic information |
| `INFO` | Normal application events |
| `WARNING` | Unexpected situation that may need attention |
| `ERROR` | An operation failed |
| `CRITICAL` | A serious failure |

Example:

```python
logging.info("User signed in")
logging.warning("Login attempt failed")
logging.error("Database operation failed")
```

Do not log passwords, API keys, access tokens, or unnecessary personal data.

## 12.2 Logging exceptions

`logging.exception()` includes exception details and a traceback when used inside an exception handler:

```python
import logging

try:
    result = 10 / 0
except Exception:
    logging.exception("An unexpected error occurred")
```

In real applications, catch specific exceptions where possible and handle them appropriately.

---

# 13. Application Logs vs Server Logs

A deployment may have several kinds of logs:

| Log type | What it can tell you |
|---|---|
| Application logs | Python messages and application errors |
| Nginx access logs | Requests, status codes, response sizes |
| Nginx error logs | Proxy failures and Nginx errors |
| Gunicorn/Uvicorn logs | Startup, worker lifecycle, server errors |
| System logs | Service failures and operating-system events |

A `502 Bad Gateway` from Nginx may mean Nginx could not successfully communicate with the application server. Check both Nginx error logs and application-server logs.

On many Linux systems:

```bash
sudo nginx -t
sudo systemctl status nginx
sudo journalctl -u nginx
```

The application service name varies. Replace `your-app` with the actual service name:

```bash
sudo systemctl status your-app
sudo journalctl -u your-app
```

These commands assume a Linux system using systemd and appropriate permissions.

# 14. Monitoring

**Monitoring** means observing an application's health and performance over time.

Logging records events. Monitoring helps identify whether the system is healthy and whether performance is changing.

Useful things to monitor:
- Availability.
- HTTP error rates.
- Response time.
- CPU and memory usage.
- Disk space.
- Database connectivity.
- Worker restarts.
- Request volume.

Example:

```text
CPU usage: high
Memory usage: normal
Response time: increasing
HTTP 500 errors: increasing
```

This helps narrow down an investigation but does not, by itself, prove the root cause.

## 14.1 Health check endpoint

A simple FastAPI health endpoint:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}
```

A monitoring system can request `/health` periodically. This basic endpoint confirms that the route can respond; a larger system may also need checks for dependencies such as the database.

## 14.2 Example monitoring tools

- **Prometheus:** Collects metrics.
- **Grafana:** Displays dashboards.
- **Sentry:** Reports application errors.
- **Cloud-provider monitoring:** Monitors services and infrastructure.
- **Uptime monitoring services:** Check whether a site is reachable.

Choose tools based on scale, budget, privacy requirements, and hosting platform.

## 14.3 Logging vs monitoring

| Logging | Monitoring |
|---|---|
| Records individual events | Tracks health and trends |
| Helps investigate a specific failure | Helps detect changes and problems |
| Example: database connection failed | Example: database errors increased over 10 minutes |
| Often includes messages and tracebacks | Often uses metrics, alerts, and dashboards |

They work together: monitoring can alert you to a problem, and logs can help explain what happened.

# 15. Deployment Checklist

## Application
- [ ] The application starts without errors.
- [ ] Development reload is disabled in production.
- [ ] Environment variables are configured.
- [ ] Secrets are not committed to Git.
- [ ] Dependencies are recorded and installed.
- [ ] Errors are handled appropriately.

## Server
- [ ] The application server is running.
- [ ] A service manager or hosting platform can restart it.
- [ ] The internal app port is not unnecessarily exposed publicly.
- [ ] Nginx or the hosting platform is configured correctly.
- [ ] Firewall rules are appropriate.

## Domain and HTTPS
- [ ] DNS points to the correct target.
- [ ] The domain is configured in the web server/platform.
- [ ] HTTPS works without certificate warnings.
- [ ] Certificate renewal is configured.

## Logging and monitoring
- [ ] Application logs are available.
- [ ] Server error logs can be inspected.
- [ ] Disk and resource usage are monitored.
- [ ] A health or uptime check is configured.
- [ ] Logs do not expose secrets or sensitive data.

# 16. Common Beginner Problems

## Problem 1: `uvicorn main:app` cannot import the application

Check:
- Is the file named `main.py`?
- Is the FastAPI object named `app`?
- Are you running the command from the correct directory?
- Are required packages installed?

If the file is named `server.py`, the command may be:

```bash
uvicorn server:app
```

Format:

```text
uvicorn module_name:application_variable
```

## Problem 2: Nginx returns `502 Bad Gateway`

Possible causes:
- Uvicorn/Gunicorn is stopped.
- Nginx forwards to the wrong port.
- The app listens on a different address.
- A Unix socket path or permission is wrong.
- The app failed during startup.

Check the application service and Nginx error logs.

## Problem 3: The domain does not open

Check DNS records, the target IP, firewall rules, Nginx domain configuration, and whether the server is running.

## Problem 4: HTTPS certificate warning

Check that the certificate matches the domain, has not expired, and is configured with the correct certificate chain. Confirm DNS points to the expected server and renewal is working.

## Problem 5: The application is slow

Check response times, CPU/memory usage, database queries, external API latency, worker configuration, and error logs. Do not simply add workers without measuring the cause.

# 18. Quick Revision

**WSGI:** Standard interface commonly used by synchronous Python web applications.

**ASGI:** Interface supporting asynchronous applications and protocols such as WebSockets.

**Gunicorn:** Application server commonly used for WSGI applications; can manage compatible ASGI workers.

**Uvicorn:** ASGI server commonly used with FastAPI and Starlette.

**Worker:** A process or worker instance that handles application work.

**Nginx:** Web server software often used as a reverse proxy and TLS endpoint.

**Reverse proxy:** A server that receives client requests and forwards them to backend services.

**Domain:** A human-readable name used to reach a service.

**DNS:** System that resolves domain names to relevant records and destinations.

**HTTPS:** HTTP protected with TLS encryption.

**SSL/TLS certificate:** A certificate used to help authenticate a server for a secure connection; modern HTTPS uses TLS.

**Logging:** Recording events and errors from an application or server.

**Monitoring:** Tracking system health and performance over time, often with metrics and alerts.
