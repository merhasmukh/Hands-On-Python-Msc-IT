# 4.4 Docker and Docker Compose


## Learning Objectives

By the end of this chapter, you should be able to:
- Explain Docker and why developers use it.
- Distinguish images, containers, Dockerfiles, and registries.
- Use common Docker commands.
- Dockerize Flask and FastAPI applications.
- Use Docker Compose to run an application and a database.
- Understand port mapping, environment variables, networks, and volumes.
- Troubleshoot common Docker issues.

# 1. What Is Docker?

**Docker** is a platform for packaging and running applications in containers.

A Python application may work on one computer but fail on another because of different Python versions, installed packages, system libraries, or configuration. Docker helps package an application and its dependencies in a consistent environment.

```text
Dockerfile
    |
    | docker build
    v
Docker Image
    |
    | docker run
    v
Running Container
```

A useful analogy: an image is like a recipe or template; a container is a running instance created from that template.

Docker improves consistency, but CPU architecture, networking, file permissions, and production settings can still matter.

# 2. Important Docker Concepts

| Term | Meaning |
|---|---|
| Dockerfile | Instructions used to build an image |
| Image | Packaged template used to create containers |
| Container | A running or stopped instance of an image |
| Registry | Place to store and download images |
| Docker Hub | A popular public image registry |
| Volume | Storage that can persist beyond a container's lifecycle |
| Port mapping | Connects a host port to a container port |
| Docker network | Allows containers to communicate |
| Docker Compose | Tool for defining and running multi-container applications |

## Image vs Container

| Image | Container |
|---|---|
| Template/package | Instance created from an image |
| Built with a Dockerfile | Created using `docker run` or Compose |
| Can be shared through a registry | Runs the application process |
| Usually unchanged while running | Has a writable container layer |

Data stored only in a container's writable layer can be lost when the container is removed. Use volumes or another persistent storage system for important data.

# 3. Install and Check Docker

Install Docker Desktop on supported Windows/macOS systems, or Docker Engine using the official instructions for your Linux distribution.

Check the installation:

```bash
docker --version
docker version
```

Run a test container:

```bash
docker run hello-world
```

Docker downloads the image if needed, creates a container, runs its program, and then the container exits.

Useful commands:

```bash
docker ps       # running containers
docker ps -a    # all containers, including stopped ones
docker images   # local images
docker info     # Docker system information
```

# 4. Useful Docker Commands

| Command | Purpose |
|---|---|
| `docker pull IMAGE` | Download an image |
| `docker run IMAGE` | Create and start a container |
| `docker stop CONTAINER` | Stop a running container |
| `docker start CONTAINER` | Start a stopped container |
| `docker restart CONTAINER` | Restart a container |
| `docker logs CONTAINER` | Show container logs |
| `docker exec -it CONTAINER sh` | Open a shell if the image includes one |
| `docker rm CONTAINER` | Remove a stopped container |
| `docker rmi IMAGE` | Remove an unused image |
| `docker inspect CONTAINER` | Show detailed container information |

## Run a container in the background

```bash
docker run -d --name web-demo nginx:stable
docker ps
docker logs web-demo
docker stop web-demo
docker rm web-demo
```

## Port mapping

A service inside a container is not automatically published on a host port. Use `-p`:

```bash
docker run -d --name web-demo -p 8080:80 nginx:stable
```

The format is:

```text
-p HOST_PORT:CONTAINER_PORT
```

Open `http://localhost:8080`. The host's port `8080` forwards to port `80` inside the container.

# 5. Dockerfile Basics

A **Dockerfile** is a text file with instructions for building an image.

| Instruction | Purpose |
|---|---|
| `FROM` | Select a base image |
| `WORKDIR` | Set the working directory |
| `COPY` | Copy files into the image |
| `RUN` | Run a command during image build |
| `ENV` | Set environment variables in the image |
| `EXPOSE` | Document the port the app listens on |
| `CMD` | Set the default command when a container starts |

Example:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

`EXPOSE` does not publish a port to the host. Use `-p` or Compose `ports` to publish a port.

## The `.dockerignore` file

This tells Docker which files to exclude from the build context:

```dockerignore
.venv/
venv/
__pycache__/
*.pyc
.git/
.env
.pytest_cache/
.DS_Store
```

`.gitignore` controls which untracked files Git normally ignores; `.dockerignore` controls which files Docker excludes from the build context. Keep secrets out of image layers and source control.

# 6. Dockerizing a Flask Application

**Dockerizing** means packaging an application into an image so it can run in a container.

## Project structure

```text
flask_demo/
├── app.py
├── requirements.txt
├── Dockerfile
└── .dockerignore
```

## `app.py`

```python
from flask import Flask
import os

app = Flask(__name__)

@app.route("/")
def home():
    return {
        "message": "Hello from Flask in Docker",
        "environment": os.getenv("APP_ENV", "development")
    }

if __name__ == "__main__":
    # For a simple local demonstration only.
    app.run(host="0.0.0.0", port=5000)
```

Flask's built-in development server is not recommended for production.

## `requirements.txt`

```text
Flask
gunicorn
```

For repeatable builds, use tested compatible package versions rather than relying indefinitely on unpinned latest versions.

## `Dockerfile`

This example uses Gunicorn as the application server:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 5000

CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]
```

`app:app` means the module `app.py` and the Flask application object named `app`.

## `.dockerignore`

```dockerignore
.venv/
__pycache__/
*.pyc
.git/
.env
```

## Build and run

Run these commands from the `flask_demo/` directory:

```bash
docker build -t flask-demo .
docker run -d --name flask-container -p 5000:5000 flask-demo
```

Visit `http://localhost:5000`.

Expected response:

```json
{
  "message": "Hello from Flask in Docker",
  "environment": "development"
}
```

Inspect logs and stop the container:

```bash
docker logs flask-container
docker stop flask-container
docker rm flask-container
```

# 7. Dockerizing a FastAPI Application

## Project structure

```text
fastapi_demo/
├── main.py

├── Dockerfile
└── .dockerignore
```

## `main.py`

```python
from fastapi import FastAPI
import os

app = FastAPI()

@app.get("/")
def home():
    return {
        "message": "Hello from FastAPI in Docker",
        "environment": os.getenv("APP_ENV", "development")
    }

@app.get("/health")

```

## `requirements.txt`

```text
fastapi
uvicorn[standard]
```

## `Dockerfile`

```dockerfile
FROM python:3.12-slim

WORKDIR /app

ENV PYTHONDONTWRITEBYTECODE=1
```

Uvicorn listens on `0.0.0.0` inside the container so that traffic forwarded by Docker can reach it.

# 8. Environment Variables in Docker

Avoid hard-coding environment-specific settings into your application. Python can read them using `os.getenv()`:

```python
import os

app_env = os.getenv("APP_ENV", "development")
```

Set an environment variable when starting a container:

```bash
docker run -d \
  --name fastapi-container \
  -p 8000:8000 \
  -e APP_ENV=production \
  fastapi-demo
```

For local development, you can pass a `.env` file:

```bash
docker run --env-file .env -p 8000:8000 fastapi-demo
```

Example `.env`:

```env
APP_ENV=development
```

Keep secret-containing `.env` files out of Git and Docker build contexts. For production, use the hosting platform's secret-management facilities where available. Do not bake passwords or API keys into a Dockerfile with `ENV` or `COPY`.

# 9. Why Docker Compose?

An application may need multiple services, such as:
- A web application
- A database
- A cache
- A background worker

**Docker Compose** defines these services in one YAML file and manages them together.

```text
             compose.yaml
             /          \
            v            v
       Web App          Database
       Container        Container
            \            /
             Docker Network
```

Compose can define services, image builds, ports, environment variables, volumes, networks, and health checks.

## Basic Compose example

Create `compose.yaml`:

```yaml
services:
  web:
    image: nginx:stable
    ports:
      - "8080:80"
```

Run:

```bash
docker compose up -d
docker compose ps
docker compose logs
docker compose down
```

`docker compose down` removes Compose-created containers and networks. Named volumes normally remain unless you explicitly remove them. Be careful with `docker compose down -v`, which removes Compose-managed volumes and can delete stored data.

# 10. Docker Compose: Flask + MySQL

This example runs a Flask app and a MySQL database together.

## Project structure

```text
flask_mysql_demo/
├── app/
│   └── app.py
├── requirements.txt
├── Dockerfile
├── compose.yaml
└── .dockerignore
```

## `app/app.py`

This example uses the PyMySQL driver:

```python
import os
import pymysql
from flask import Flask, jsonify

app = Flask(__name__)

def get_connection():
    return pymysql.connect(
        host=os.getenv("DB_HOST", "db"),
        user=os.getenv("DB_USER", "appuser"),
        password=os.getenv("DB_PASSWORD", ""),
        database=os.getenv("DB_NAME", "studentdb"),
        cursorclass=pymysql.cursors.DictCursor,
        connect_timeout=5
    )

@app.get("/")
def home():
    return jsonify({"message": "Flask + MySQL using Docker Compose"})

@app.get("/db-check")
def db_check():
    try:
        connection = get_connection()
        try:
            with connection.cursor() as cursor:
                cursor.execute("SELECT 1 AS result")
                result = cursor.fetchone()
            return jsonify({
                "database": "connected",
                "result": result["result"]
            })
        finally:
            connection.close()
    except Exception:
        app.logger.exception("Database check failed")
        return jsonify({"database": "unavailable"}), 503
```

The client receives a generic error while details are written to server logs. A production application should handle errors carefully and never expose credentials or internal exception details.

## `requirements.txt`

```text
Flask
gunicorn
PyMySQL
```

## `Dockerfile`

```dockerfile
FROM python:3.12-slim

WORKDIR /app

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ ./app/

EXPOSE 5000

CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]
```

## `compose.yaml`

This uses sample credentials for a local teaching exercise only. Do not reuse these values in production.

```yaml
services:
  web:
    build: .
    ports:
      - "5000:5000"
    environment:
      DB_HOST: db
      DB_NAME: studentdb
      DB_USER: appuser
      DB_PASSWORD: local-example-password
    depends_on:
      db:
        condition: service_healthy

  db:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: studentdb
      MYSQL_USER: appuser
      MYSQL_PASSWORD: local-example-password
      MYSQL_ROOT_PASSWORD: local-root-example-password
    volumes:
      - mysql_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "root", "-p$${MYSQL_ROOT_PASSWORD}"]
      interval: 5s
      timeout: 5s
      retries: 20

volumes:
  mysql_data:
```

### Understand the configuration

- `web` is the Flask service.
- `db` is the MySQL service.
- `DB_HOST: db` uses the Compose service name as the hostname.
- `depends_on` with `service_healthy` waits for the database health check before starting the web service.
- `mysql_data` is a named volume that keeps database files beyond the lifecycle of a container.
- `$$` prevents Compose from substituting the variable before the health-check command runs inside the container.
- Replace sample credentials and use proper secret management outside local exercises.

## `.dockerignore`

```dockerignore
.venv/
__pycache__/
*.pyc
.git/
.env
```

## Start and test

Run from the directory containing `compose.yaml`:

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f
```

Open:
- `http://localhost:5000`
- `http://localhost:5000/db-check`

When the database is ready, `/db-check` should return a response similar to:

```json
{
  "database": "connected",
  "result": 1
}
```

Stop the project:

```bash
docker compose down
```

This keeps the named `mysql_data` volume. To remove it too:

```bash
docker compose down -v
```

**Warning:** `-v` deletes the Compose-managed database volume and its data. Do not use it when you need to keep the database.

# 11. Compose Example: FastAPI + PostgreSQL

A typical arrangement:

```text
FastAPI Container
      |
      | DB_HOST=db
      v
PostgreSQL Container
      |
      v
Named Volume
```

Example `compose.yaml`:

```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DB_HOST: db
      DB_NAME: appdb
      DB_USER: appuser
      DB_PASSWORD: local-example-password
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: local-example-password
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 5s
      timeout: 5s
      retries: 20

volumes:
  postgres_data:
```

This is a Compose configuration example, not a complete FastAPI database application. The Python app also needs PostgreSQL connection code and a compatible driver. Replace sample credentials and use suitable secrets handling.

# 12. Container Networking

Compose creates a network for a project by default. Services can generally reach each other by service name.

For example:

```text
web container ---> db:3306
```

Inside the web container, use:

```env
DB_HOST=db
```

Do not normally use `DB_HOST=localhost` to reach a different container. Inside a container, `localhost` refers to that same container.

In the Flask + MySQL example, the database port is not published to the host. This is a reasonable default for a local web-app/database exercise.

# 13. Volumes and Persistent Data

A **volume** stores data separately from a container's writable layer.

Example:

```yaml
services:
  db:
    image: mysql:8.4
    volumes:
      - mysql_data:/var/lib/mysql

volumes:
  mysql_data:
```

Without persistent storage, removing a database container can lose data stored only in its writable layer. Volumes are not a substitute for backups; important data needs a tested backup and recovery plan.

# 14. Environment Variables and Secrets in Compose

A Compose file can set environment variables:

```yaml
services:
  web:
    environment:
      APP_ENV: development
      DB_HOST: db
```

For local learning, a Compose `.env` file can provide values for substitution in the Compose YAML. It is not automatically passed to every container unless you use `environment` or `env_file`.

Example `.env`:

```env
MYSQL_DATABASE=studentdb
MYSQL_USER=appuser
MYSQL_PASSWORD=replace-with-a-local-password
MYSQL_ROOT_PASSWORD=replace-with-a-local-root-password
```

Compose service:

```yaml
services:
  db:
    image: mysql:8.4
    env_file:
      - .env
```

Add secret-containing files to `.gitignore` and `.dockerignore`. Environment variables can be visible to privileged users and diagnostic tools, so production secrets should be managed carefully.

Run these from the folder containing the Compose file.

|---|---|
| `docker compose up` | Create/start services and show logs |
| `docker compose up -d` | Start services in the background |
| `docker compose up --build -d` | Build/rebuild images and start services |
| `docker compose ps` | Show service status |
| `docker compose logs` | Display logs |
| `docker compose logs -f web` | Follow web-service logs |
| `docker compose exec web sh` | Open a shell if available |

# 16. Common Beginner Problems

## Problem 1: Port is already allocated

Another process is using the host port. Choose a different host port:

```bash
docker run -p 8081:5000 flask-demo
```

Then open `http://localhost:8081`.

## Problem 2: Container exits immediately

Inspect the logs:

```bash
docker logs CONTAINER_NAME
```

Possible causes include syntax errors, missing packages, incorrect startup commands, wrong module/object names, or missing environment variables.

## Problem 3: The app cannot connect to the database

Check:
- Are both services running?
- Is the database healthy?
- Is the hostname the Compose service name, such as `db`?
- Are database names and credentials consistent?
- Is the correct database driver installed?
- Is the database ready to accept connections?

## Problem 4: Code changes are not visible

If source code was copied into the image at build time, rebuild:

```bash
docker compose up --build -d
```

Bind mounts can share local code with a container during development, but they must be configured carefully.

## Problem 5: Database data disappeared

Check whether a named volume was configured, whether `docker compose down -v` was run, and whether the app was connected to the expected database. Use backups for important data.

## Problem 6: `localhost` is the wrong database hostname

Inside a container, `localhost` refers to that container. Use the Compose service name:

```env
DB_HOST=db
```
