# 4.1 Project Organization

## Learning Objectives

After studying this chapter, you should be able to:

- Organize a Python project using a clean folder structure.
- Understand the purpose of configuration files.
- Understand environment variables.
- Use `.env` files with `python-dotenv`.
- Handle passwords, API keys, and other secrets safely.
- Understand the basic ideas behind the Twelve-Factor App methodology.

---

# 1. What is Project Organization?

**Project organization** means arranging the files and folders of a software project in a logical way.

A small Python program may have only one file:

```text
hello.py
```

But a real application may contain:

- Python source code
- Configuration
- Database code
- HTML templates
- CSS/JavaScript
- Tests
- Documentation
- Environment variables
- Dependencies

If everything is placed in one folder without any structure, the project becomes difficult to understand and maintain.

A good project structure makes it easier to:

- Find files
- Add new features
- Fix bugs
- Work with other developers
- Test the application
- Deploy the application

---

# 2. Basic Project Folder Structure

A simple Python project might look like this:

```text
student_app/
│
├── app/
│   ├── __init__.py
│   ├── main.py
│   ├── config.py
│   └── database.py
│
├── tests/
│   └── test_main.py
│
├── .env
├── .gitignore
├── requirements.txt
├── README.md
└── run.py
```

Let's understand the important files.

| File/Folder | Purpose |
|---|---|
| `app/` | Main application code |
| `main.py` | Application entry point or main logic |
| `config.py` | Configuration-related code |
| `database.py` | Database-related code |
| `tests/` | Automated tests |
| `.env` | Local environment variables/secrets |
| `.gitignore` | Files Git should ignore |
| `requirements.txt` | Python dependencies |
| `README.md` | Project documentation |
| `run.py` | Optional script used to start the application |

> The exact structure can change depending on the framework and project size.

---

# 3. Why Should We Separate Files?

Suppose we put everything into:

```text
main.py
```

It might contain:

```python
database code
API routes
configuration
authentication
business logic
file handling
```

As the project grows, `main.py` can become thousands of lines long.

Instead, we can separate responsibilities:

```text
app/
├── main.py
├── database.py
├── auth.py
├── users.py
└── config.py
```

This follows a simple idea:

> **One file/module should have a clear responsibility.**

---

# 4. Configuration Files

Configuration means the settings that control how an application works.

Examples:

```text
Application name
Database URL
API URL
Debug mode
Port number
Secret key
External API key
```

For example:

```python
DEBUG = True
PORT = 8000
DATABASE_URL = "sqlite:///app.db"
```

These values are configuration.

## Why separate configuration?

Instead of writing settings throughout the application:

```python
if DEBUG:
    ...
```

we can keep them in one place:

```text
app/
├── main.py
└── config.py
```

Example:

```python
# config.py

DEBUG = True
PORT = 8000
```

Then:

```python
# main.py

from config import DEBUG, PORT

print(DEBUG)
print(PORT)
```

---

# 5. Configuration vs Secret

This distinction is important.

### Configuration

A normal configuration value might be:

```text
PORT=8000
DEBUG=True
APP_NAME=StudentApp
```

### Secret

A secret is sensitive information such as:

```text
DATABASE_PASSWORD
API_KEY
SECRET_KEY
ACCESS_TOKEN
```

For example:

```text
API_KEY=abc123...
```

An API key should **not** normally be written directly inside source code.

Bad:

```python
API_KEY = "my-secret-api-key"
```

Better:

```python
API_KEY = os.getenv("API_KEY")
```

---

# 6. Environment Variables

An **environment variable** is a value stored outside the Python source code and made available to the application by the operating system or deployment environment.

For example:

```text
APP_NAME=StudentApp
PORT=8000
DEBUG=True
```

Python can read environment variables using the `os` module.

```python
import os

app_name = os.getenv("APP_NAME")

print(app_name)
```

If the environment contains:

```text
APP_NAME=StudentApp
```

the output is:

```text
StudentApp
```

---

# 7. `os.getenv()`

The basic syntax is:

```python
os.getenv("VARIABLE_NAME")
```

Example:

```python
import os

database_url = os.getenv("DATABASE_URL")

print(database_url)
```

You can also provide a default value:

```python
port = os.getenv("PORT", "8000")

print(port)
```

If `PORT` does not exist, Python uses:

```text
8000
```

---

# 8. Why Use Environment Variables?

Consider this code:

```python
API_KEY = "123456789"
```

Problems:

1. The key is visible in the source code.
2. It can accidentally be uploaded to GitHub.
3. Different developers may need different values.
4. Development and production may use different settings.

Instead:

```python
API_KEY = os.getenv("API_KEY")
```

Now the value can be supplied by the environment.

---

# 9. The `.env` File

During development, it is convenient to keep environment variables in a file called:

```text
.env
```

Example:

```env
APP_NAME=StudentApp
DEBUG=True
PORT=8000
API_KEY=my-secret-key
```

A `.env` file is simply a text file containing key-value pairs.

The general format is:

```text
NAME=value
```

For example:

```env
DATABASE_URL=sqlite:///app.db
DEBUG=True
PORT=8000
```

---

# 10. `.env` Is Not Automatically Read by Python

This is an important beginner concept.

Python's:

```python
os.getenv()
```

does not automatically read a `.env` file.

We can use the package:

```text
python-dotenv
```

Install it:

```bash
pip install python-dotenv
```

---

# 11. Using `python-dotenv`

Example `.env`:

```env
APP_NAME=StudentApp
API_KEY=my-secret-key
```

Python:

```python
import os
from dotenv import load_dotenv

load_dotenv()

app_name = os.getenv("APP_NAME")
api_key = os.getenv("API_KEY")

print(app_name)
print(api_key)
```

Output:

```text
StudentApp
my-secret-key
```

### What happens?

The process is:

```text
.env
  │
  ▼
load_dotenv()
  │
  ▼
Environment Variables
  │
  ▼
os.getenv()
  │
  ▼
Python Application
```

# 12. A Small Practical Example

Project:

```text
student_app/
├── app.py
├── .env
└── requirements.txt
```

### `.env`

```env
APP_NAME=Student Management System
DEBUG=True
```

### `app.py`

```python
import os
from dotenv import load_dotenv

load_dotenv()

app_name = os.getenv("APP_NAME")
debug = os.getenv("DEBUG")

print("Application:", app_name)
print("Debug:", debug)
```

Output:

```text
Application: Student Management System
Debug: True
```

# 13. Environment Variables Are Strings

This is another important point.

Suppose:

```env
PORT=8000
DEBUG=True
```

When Python reads them:

```python
port = os.getenv("PORT")
debug = os.getenv("DEBUG")
```

both values are strings.

So:

```python
print(type(port))
print(type(debug))
```

will produce:

```text
<class 'str'>
<class 'str'>
```

If you need an integer:

```python
port = int(os.getenv("PORT", "8000"))
```

For a Boolean, you should convert it carefully:

```python
debug = os.getenv("DEBUG", "False").lower() == "true"
```

---

# 14. `.env` and `.gitignore`

Suppose your project contains:

```text
.env
```

and `.env` contains:

```env
API_KEY=very-secret-value
DATABASE_PASSWORD=my-password
```

You should normally **not upload `.env` to GitHub**.

Add this to `.gitignore`:

```gitignore
.env
```

Now Git will ignore the `.env` file.

---

# 15. Secrets Handling

A **secret** is sensitive information that should be protected.

Examples:

- API keys
- Database passwords
- JWT signing secrets
- Cloud credentials
- Access tokens
- Private keys

## Bad practice

```python
API_KEY = "sk-123456789"
```

## Better

```python
import os

API_KEY = os.getenv("API_KEY")
```

And locally:

```env
API_KEY=sk-123456789
```

with `.env` excluded from Git.

---

# 16. Never Commit Secrets

Avoid this:

```text
git add .
git commit -m "add api key"
git push
```

If `.env` is not ignored, your secret may be uploaded.

Even worse, deleting the file later does not necessarily mean the secret has disappeared from Git history.

If a real API key has accidentally been exposed:

1. Revoke/rotate the key.
2. Generate a new key.
3. Remove the secret from the repository/history as appropriate.
4. Update the application with the new secret.

> **Do not assume that making a GitHub repository private makes careless secret handling safe.**

---

# 17. `.env.example`

If `.env` is ignored, another developer still needs to know which variables are required.

A useful solution is:

```text
.env.example
```

Example:

```env
APP_NAME=StudentApp
DEBUG=False
PORT=8000
API_KEY=your-api-key-here
DATABASE_URL=your-database-url
```

This file can safely be committed because it contains placeholders rather than real secrets.

The developer can copy it:

```bash
cp .env.example .env
```

Then fill in the actual values.

On Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

---

# 18. `requirements.txt`

Python projects often use external packages.

For example:

```text
fastapi
uvicorn
python-dotenv
```

These dependencies can be stored in:

```text
requirements.txt
```

Example:

```text
fastapi==0.116.1
uvicorn==0.35.0
python-dotenv==1.1.1
```

Install them using:

```bash
pip install -r requirements.txt
```

A common workflow is:

```text
Create virtual environment
        ↓
Install packages
        ↓
Develop application
        ↓
Create/update requirements.txt
        ↓
Another developer installs requirements
```

You can generate a requirements file using:

```bash
pip freeze > requirements.txt
```

# 20. A More Complete Python Project

A beginner-friendly structure can look like:

```text
student_app/
│
├── app/
│   ├── __init__.py
│   ├── main.py
│   ├── config.py
│   └── database.py
│
├── tests/
│   └── test_main.py

├── .env
├── .env.example
├── .gitignore
├── requirements.txt
└── README.md
```

The important idea is not memorizing the exact structure.

Instead, understand:

> **Organize files according to their responsibility.**

# 21. Twelve-Factor App Principles

The **Twelve-Factor App** is a methodology for building modern applications that are easier to develop, deploy, scale, and maintain.

The twelve factors are:

1. Codebase
2. Dependencies
3. Config
4. Backing services
5. Build, release, run
6. Processes
7. Port binding
8. Concurrency
9. Disposability
10. Dev/prod parity
11. Logs
12. Admin processes

For beginners, we will focus especially on the ideas related to project organization and configuration.

---

## 21.1 Codebase

Keep the application's source code under version control.

Example:

```text
Git Repository
      │
      ▼
Python Project
```

Git allows developers to track changes to the code.

---

## 21.2 Dependencies

Explicitly declare the packages your application needs.

For Python:

```text
requirements.txt
```

Example:

```text
fastapi
uvicorn
python-dotenv
```

Instead of assuming that every computer already has the required packages installed.

---

## 21.3 Config

Configuration that changes between environments should be separated from code.

For example:

```text
Development
    DATABASE_URL=local_database
    DEBUG=True

Production
    DATABASE_URL=production_database
    DEBUG=False
```

The application code can remain the same.

---

## 21.4 Backing Services

Applications often depend on external services.

Examples:

```text
MySQL
PostgreSQL
Redis
Qdrant
Cloud Storage
External APIs
```

These should be treated as external resources rather than being tightly hard-coded into the application.

For example:

```env
DATABASE_URL=...
REDIS_URL=...
```

---

## 21.5 Build, Release, Run

The application lifecycle can be thought of as:

```text
Source Code
    ↓
Build
    ↓
Release
    ↓
Run
```

This separation helps create predictable deployments.

---

## 21.6 Processes

Applications should ideally run as processes that do not depend on manually changing files on the server.

For example:

```text
Web Process
Worker Process
Background Process
```

---

## 21.7 Port Binding

A web application should be able to listen on a port.

For example:

```text
http://localhost:8000
```

The port can be configurable:

```env
PORT=8000
```

---

## 21.8 Logs

Application logs should record useful information about what is happening.

Example:

```python
import logging

logging.basicConfig(level=logging.INFO)

logging.info("Application started")
```

Avoid using only `print()` statements for serious applications.

---

# 22. Development vs Production

A common mistake is hard-coding development settings.

For example:

```python
DEBUG = True
```

Production may require:

```python
DEBUG = False
```

Instead, configuration can come from the environment:

```env
DEBUG=True
```

or:

```env
DEBUG=False
```

The same code can then be used in different environments.

```text
             Same Code
                 │
        ┌────────┴────────┐
        ▼                 ▼
   Development        Production
        │                 │
 DEBUG=True          DEBUG=False
```

# 23. Recommended `.gitignore` for Python

A simple Python `.gitignore`:

```gitignore
# Environment variables
.env

# Virtual environment
.venv/
venv/

# Python cache
__pycache__/
*.py[cod]

# Test/cache files
.pytest_cache/

# IDE settings
.vscode/
.idea/

# OS files
.DS_Store
Thumbs.db

# Local database
*.sqlite3

# Secrets
*.pem
*.key
```

> Be careful with patterns such as `*.key` or `*.pem`; only ignore them if those files are actually local secrets/private keys in your project.

# 24. Common Beginner Mistakes

## Mistake 1: Hard-coding API keys

Bad:

```python
API_KEY = "secret-key"
```

Better:

```python
API_KEY = os.getenv("API_KEY")
```

---

## Mistake 2: Committing `.env`

Bad:

```text
git add .
git commit
git push
```

when `.env` contains secrets and is not ignored.

Better:

```gitignore
.env
```

---

## Mistake 3: Confusing `.env` with production secret management

A `.env` file is convenient for local development.

For production, organizations may use dedicated secret/configuration systems provided by their hosting platform or cloud provider.

---

## Mistake 4: Putting everything in `main.py`

Large applications become difficult to maintain.

Separate responsibilities into modules.

---

## Mistake 5: Not documenting required variables

Use:

```text
.env.example
```

to document the required environment variables.

A local file commonly used to store environment variables during development.
