# 4.2 Version Control: Git and GitHub

## Learning Objectives

After studying this chapter, you should be able to:

- Explain what version control is.
- Understand Git and GitHub.
- Create a Git repository.
- Track and commit changes.
- Understand the staging area.
- Use branches.
- Create and merge branches.
- Understand Pull Requests.
- Collaborate with other developers.
- Use `.gitignore`.
- Write clean commit messages.
- Understand a basic Git/GitHub workflow.

---

# 1. What is Version Control?

**Version control** is a system for tracking changes to files over time.

Imagine you are working on:

```text
app.py
```

You change the code today.

Tomorrow you change it again.

Later you realize:

> "The old version was working better!"

Without version control, finding the old version can be difficult.

With version control, you can see:

```text
Version 1
   ↓
Version 2
   ↓
Version 3
   ↓
Version 4
```

You can inspect changes and, when appropriate, return to an earlier version.

---

# 2. Why Do We Need Version Control?

Version control helps with:

- Tracking changes
- Recovering older versions
- Collaboration
- Experimenting safely
- Finding who changed something
- Maintaining project history
- Managing different features

For a team:

```text
Developer A ──┐
Developer B ──┼──> Shared Repository
Developer C ──┘
```

---

# 3. What is Git?

**Git** is a distributed version control system.

It runs on your computer and tracks changes in your project.

For example:

```text
student_app/
├── app.py
├── config.py
└── README.md
```

Git can track changes to these files.

---

# 4. What is GitHub?

**GitHub** is a platform that hosts Git repositories online and provides collaboration features.

A simple way to remember:

```text
Git
↓
Version control software

GitHub
↓
Online platform for Git repositories and collaboration
```

Git can work without GitHub.

For example:

```text
Your Computer
     ↓
    Git
```

GitHub adds online collaboration:

```text
Your Computer
     ↓
    Git
     ↓
  GitHub
     ↑
    Git
     ↑
Other Developer
```

---

# 5. Git vs GitHub

| Git | GitHub |
|---|---|
| Version control system | Hosting/collaboration platform |
| Runs locally | Runs primarily as an online service |
| Tracks file changes | Hosts Git repositories |
| Works without GitHub | Uses Git repositories |
| Provides commits/branches | Provides Pull Requests/issues/reviews |

# 7. Configure Git

Set your name:

```bash
git config --global user.name "Your Name"
```

Set your email:

```bash
git config --global user.email "you@example.com"
```

Check the configuration:

```bash
git config --global --list
```

Use the email associated with your Git hosting account where appropriate.

# 8. Create a Git Repository

Suppose you have:

```text
student_app/
├── app.py
└── README.md
```

Go into the project:

```bash
cd student_app
```

Initialize Git:

```bash
git init
```

Git creates a hidden directory:

```text
.git/
```

This directory contains Git's internal repository information.

Do not manually edit `.git` unless you know what you are doing.

---

# 9. Check Repository Status

Run:

```bash
git status
```

You may see:

```text
Untracked files:
    app.py
    README.md
```

This means Git sees the files but they are not yet being tracked in a commit.

---

# 10. The Three Important Git Areas

A beginner should understand these three areas:

```text
Working Directory
       ↓
   git add
       ↓
Staging Area
       ↓
  git commit
       ↓
Repository
```

### Working Directory

The files you are currently editing.

### Staging Area

Files selected for the next commit.

### Repository

The Git history containing commits.

---

# 11. `git add`

To stage one file:

```bash
git add app.py
```

To stage multiple files:

```bash
git add app.py README.md
```

To stage all appropriate changes:

```bash
git add .
```

Then check:

```bash
git status
```

---

# 12. `git commit`

A **commit** records a set of changes in Git history.

Example:

```bash
git commit -m "Add student registration form"
```

The `-m` option provides the commit message.

Think of a commit as:

> A named checkpoint in your project history.

---

# 13. The Basic Git Workflow

The most important beginner workflow:

```text
Edit files
   ↓
git status
   ↓
git add
   ↓
git commit
   ↓
git status
```

Example:

```bash
git status
git add .
git commit -m "Add student model"
git status
```

---

# 14. View Commit History

Use:

```bash
git log
```

A shorter version:

```bash
git log --oneline
```

Example:

```text
a81c23d Add student model
b12a5ef Add login page
c72d981 Initial project setup
```

Each commit has a unique identifier.

---

# 15. Why Commit Messages Matter

Consider:

```text
update
changes
final
new
test
```

These messages do not explain much.

Better:

```text
Add student registration API
Fix invalid login validation
Update README installation steps
Add password validation
```

A good commit message tells you:

> **What changed?**

---

# 16. Commit Hygiene

**Commit hygiene** means maintaining a clean and understandable Git history.

Good commits should be:

- Small enough to understand
- Focused on one logical change
- Descriptive
- Related to a meaningful task

### Bad

```text
git commit -m "changes"
```

### Better

```text
git commit -m "Add email validation"
```

### Even better workflow

Instead of one huge commit:

```text
Add login
Add registration
Fix CSS
Change database
Update README
Fix another bug
```

you might create logical commits:

```text
Add user registration
Add login authentication
Fix login validation
Update README setup instructions
```

---

# 17. What Should Not Be Committed?

Do not normally commit:

```text
.env
__pycache__/
.venv/
large temporary files
IDE-specific files
local databases (when inappropriate)
build/cache files
secret credentials
```

This is where `.gitignore` is useful.

---

# 18. `.gitignore`

`.gitignore` tells Git which files or directories should not normally be tracked.

Example:

```gitignore
.env
.venv/
__pycache__/
*.pyc
.vscode/
.idea/
.DS_Store
```

For a Python project:

```text
student_app/
├── app.py
├── .env
├── .gitignore
└── .venv/
```

Git can ignore:

```text
.env
.venv/
```

while tracking:

```text
app.py
.gitignore
```

---

# 19. Important `.gitignore` Point

`.gitignore` generally prevents **untracked** files from being added.

Suppose you already committed:

```text
.env
```

Then later add:

```gitignore
.env
```

Git may continue tracking the already-tracked file.

You may need to remove it from Git's index:

```bash
git rm --cached .env
```

Then commit:

```bash
git commit -m "Stop tracking environment file"
```

If the file contained a real secret, you should also rotate/revoke the exposed secret.

# 20. What is a Branch?

A **branch** is an independent line of development.

Suppose the main project is:

```text
main
 │
 ├── Commit A
 ├── Commit B
 └── Commit C
```

You want to develop a new login feature.

Create a branch:

```text
main
 │
 ├── Commit A
 ├── Commit B
 └── Commit C
          \
           login-feature
              │
              ├── Commit D
              └── Commit E
```

Now you can work on the feature without directly changing the main branch.

---

# 21. Why Use Branches?

Branches are useful for:

- New features
- Bug fixes
- Experiments
- Team collaboration
- Code review

Examples:

```text
main
feature/login
feature/student-search
bugfix/password-validation
```

---

# 22. Create a Branch

Modern Git:

```bash
git switch -c feature/login
```

Another common command:

```bash
git checkout -b feature/login
```

The first command is easier to understand for beginners because `switch` clearly indicates branch switching.

---

```bash
git branch
```

Example:


The `*` shows the current branch.

# 24. Switch Branches

Switch to `main`:

```bash
git switch main
```

Switch to login feature:


# 25. A Typical Feature Workflow

Suppose you want to add a search feature.

Start from updated `main`:

```bash
git switch main
```

Create a branch:

```bash
git switch -c feature/student-search
```

Develop the feature.

Then:

```bash
git add .
git commit -m "Add student search feature"
```

Push the branch:

```bash
git push -u origin feature/student-search
```

Then create a Pull Request on GitHub.

---

# 26. What is a Remote Repository?

A **remote repository** is a Git repository stored somewhere outside your local computer.

For example:

```text
Local Repository
      │
      │ push
      ▼
GitHub Repository
```

The common remote name is:

```text
origin
```

---

# 27. Connect a Local Repository to GitHub

After creating an empty repository on GitHub, you can add it as a remote.

Example:

```bash
git remote add origin https://github.com/USERNAME/student_app.git
```

Check:

```bash
git remote -v
```

---

# 28. Push

`git push` sends local commits to the remote repository.

Example:

```bash
git push -u origin main
```

After the first push, often:

```bash
git push
```

is enough.

For a feature branch:

```bash
git push -u origin feature/login
```

---

# 29. Pull

`git pull` downloads changes from the remote repository and integrates them into your current branch.

Example:

```bash
git pull
```

Typical situation:

```text
GitHub
  │
  │ pull
  ▼
Your Computer
```

---

# 30. Fetch vs Pull

These commands are related but different.

### `git fetch`

Downloads information about remote changes without automatically integrating them into your current branch.

```bash
git fetch
```

### `git pull`

Usually performs a fetch and then integrates the changes.

```bash
git pull
```

For beginners, remember:

```text
fetch = get information/changes

pull = get + integrate
```

---

# 31. What is a Pull Request?

A **Pull Request (PR)** is a request to merge changes from one branch into another branch.

For example:

```text
feature/login
      │
      │ Pull Request
      ▼
    main
```

A Pull Request allows the team to:

- Review code
- Discuss changes
- Run automated checks
- Request modifications
- Approve changes
- Merge the feature

---

# 32. Pull Request Workflow

Typical workflow:

```text
Create branch
     ↓
Write code
     ↓
Commit changes
     ↓
Push branch
     ↓
Create Pull Request
     ↓
Code review
     ↓
Fix requested changes
     ↓
Approval
     ↓
Merge
```

---

# 33. Example Pull Request

Suppose you have:

```text
main
```

and create:

```text
feature/student-search
```

After implementing the feature:

```bash
git add .
git commit -m "Add student search feature"
git push -u origin feature/student-search
```

On GitHub, create a Pull Request:

```text
feature/student-search → main
```

A teammate reviews the code.

If changes are requested, you modify the same branch:

```bash
git add .
git commit -m "Improve student search validation"
git push
```

The Pull Request is automatically updated.

# 34. Collaboration with GitHub

Suppose three developers work on a project:

```text
Developer A → Login
Developer B → Student module
Developer C → Reports
```

They can create branches:

```text
main
├── feature/login
├── feature/students
└── feature/reports
```

Each developer works on a separate branch.

They then create Pull Requests.

This reduces the need for everyone to directly modify `main`.

# 37. Keeping Your Branch Updated

While you are working, other developers may change `main`.

You should periodically update your local `main`:

```bash
git switch main
git pull
```

Then update your feature branch using an appropriate strategy.

For a beginner-friendly workflow, one option is:

```bash
git switch feature/student-search
git merge main
```

Now your feature branch contains the latest `main` changes.

# 38. Merge Conflicts

A **merge conflict** occurs when Git cannot automatically combine changes.

Example:

Developer A changes:

```python
message = "Hello Student"
```

Developer B changes the same line:

```python
message = "Welcome Student"
```

Git may not know which version should be kept.

It reports a conflict.

You then manually decide which code is correct.

---

# 39. What a Conflict Looks Like

You may see:

```text
<<<<<<< HEAD
message = "Hello Student"
=======
message = "Welcome Student"
>>>>>>> main
```

You must edit the file and keep the desired version.

For example:

```python
message = "Welcome Student"
```

Then:

```bash
git add .
git commit -m "Resolve merge conflict"
```

# 42. Atomic Commits

An **atomic commit** represents one logical change.

For example:

```text
Add student model
```

should ideally contain the changes required for that feature, rather than unrelated changes such as:

```text
Add student model
Change website colors
Update README
Fix unrelated login bug
```

Keeping commits focused makes review and troubleshooting easier.

---

# 43. Do Not Commit Temporary Work

Avoid commits containing:

```text
print("testing")
temporary files
debug output
unused code
local passwords
API keys
large generated files
```

Clean the project before committing.

# 50. Common Beginner Mistakes

## Mistake 1: Using Git without checking status

Always understand what Git sees:

```bash
git status
```

---

## Mistake 2: Committing everything blindly

Instead of immediately:

```bash
git add .
```

for important work, first inspect:

```bash
git status
git diff
```

Then stage the intended changes.

---

## Mistake 3: Committing secrets

Never commit:

```text
.env
API keys
passwords
private credentials
```

Use `.gitignore` and environment variables.

---

## Mistake 4: Working directly on main

For collaborative development, prefer:

```text
main
  ↓
feature branch
  ↓
Pull Request
  ↓
review
  ↓
merge
```

---

## Mistake 5: Huge commits

Avoid:

```text
git commit -m "Complete entire project"
```

when the commit contains dozens of unrelated changes.

Prefer smaller logical commits.

---

## Mistake 6: Poor commit messages

Avoid:

```text
update
final
changes
```

Prefer:

```text
Add student registration API
Fix invalid email validation
Update project installation guide
```
